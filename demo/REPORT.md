- 日期：**2026-09-15**
- 目的：验证 [DESIGN §1.8](../docs/DESIGN.md) 的页面设计**形态能否真落地**。§1.8 此前**全程只有推理、没有跑过**。

## 二、发现（对 §1.8 的修正）

### 1. ⚠️ 响应式**不是**渲染器自动给的 —— §1.8 性质 1 需要限定

§1.8 原文：「宽屏左右分栏、窄屏堆叠是**渲染器的决定**」。

**实测：窄屏（420px）下 `Grid(columns=5)` 不会重排**，只是把 5 列挤成一团、文字折成三行。`Stack(direction=horizontal)` 会 wrap（日期区两个输入框确实换行了），但 **Grid 的列数是固定的**。

> **修正**：渲染器决定「怎么画」，**不负责「重新编排」**。窄屏可用性要么由**映射层给出模式级降级**（如"窄屏用卡片列表代替表格"），要么由 **catalog 提供响应式组件**。§1.8 性质 1 的表述需要收窄。

### 2. `children` 在 schema 里**必填**，TS 类型却标可选

TS 写 `children?: string[]`，但 `catalog.validate()` 要求每个元素都有 `children`（数组）。**首轮三屏全部校验失败**，补上空数组才通过。

> 这正是「prompt 负责生成得像，校验负责生成得对」的价值——**以校验器为准，不以类型标注为准**。

### 3. catalog 的词是 **UI 原语**，不是语义件 —— 三层图要改画法

§1.8 的三层里，catalog 被描述为「**语义词表**（数据表格/表单/详情/统计块）→ 组件实现」。

**实测：`@json-render/shadcn` 的 36 个词全是原语**（Card / Stack / Grid / Button / Table / Input…），**没有"数据表格""表单"这种语义件**。

所以「语义件 → 原语组合」的全部知识**压在了映射层**——这正是 §1.8 成本表里那 200–400 行「语义件映射」。

> **修正**：三层图实际是**两层**——`语义件 ──映射层──> 原语组件树 ──渲染器──> 视觉`。
> §1.8 说的「catalog 薄封装」在 json-render 上**是空的**（直接用现成原语目录）。
> 这不影响可行性，但改变了成本归属：**要写的全在映射层**，写的是"语义件怎么拆成原语"。

### 4. `Table` 是静态的，且**单元格里放不了按钮**

`Table.props = {columns: string[], rows: string[][], caption}` —— 纯字面量，**没有数据绑定**，也没有行内操作位。

带行操作的表格只能**由 Grid/Stack 组合出来**（本 demo 的做法：`Stack[表头 Grid, Separator, 逐行 Grid]`，行操作是 Grid 里一个真按钮）。

> 意味着「数据表格」这个语义件在 catalog 里**没有对应物**，组合逻辑落在映射层。

### 5. 日期字段**没有原生控件**

`Input.type` 只接受 `text | number | email | password`。语义件有「日期」「日期区间」类型，控件层接不住 → 本 demo 降级为文本 + `YYYY-MM-DD` 占位。

### 6. 失败分支：表达力够，但**约定是隐式的**

`onError` 只有 `{set: 静态值}` 或 `{action}`（**不带失败原因**）两种形态，看似接不住 §1.8 的 `on_failure: [{when: R#, feedback, target}]`。

**实际可行**：`set` 支持魔值 `"$error.message"` —— 取抛出异常的 message。于是：

- 宿主只 `throw new Error('R1')`（**不写 state、不写措辞**）
- 映射层生成 `onError: {set: {"/scr2/failure": "$error.message"}}`
- 每条失败规则的反馈是树里一个 `Alert` + `visible: {$state: "/scr2/failure", eq: "R1"}`，并**按 `target` 锚到对应字段下方**

> **「结果」层完全声明在映射层**——这是本次实测最漂亮的一处。
> **但**：「抛出的 message 恰好是规则号」是个**隐式约定，没有 schema 约束**。需要补一条纪律或确定性校验（否则宿主抛个中文错误信息，`visible` 条件永远不成立、且**静默**）。

### 7. 跨屏数据流需要显式建模

结果页要显示"用户刚提交的值"，需要两件事，§1.8 都没提：

1. **所有屏共用一个 store**（每屏一个独立 store 时，结果页读不到表单屏的 state）
2. **语义件里要区分「样例数据」与「提交上来的值」** —— 本 demo 用 `value_from: "submission.F-TO"`，映射层负责解析成"承载该字段的那一屏的表单状态路径"

## 三、未验证 / 偏离

**未验证**（本 demo 没走到，不代表不行）：

- `repeat` + `$item` 的**动态行数**绑定 —— 本 demo 的行是映射期从数据展开的（确定性更好、且能过校验）
- §1.8 提到的「**多状态静态图**」
- 复杂布局模式：**主从 / 分步 / 看板**（只验了 列表页 / 表单页 / 结果页）
- 组件树 schema 的**版本演进**（`schema_version` 目前是摆设，没有兼容性策略）
- 复杂语义件：统计块 / 图表 / 富文本

**偏离**（formal 实现时应改）：

- DTCG → CSS 用了**自写的等价小工具**（`tokens/dtcg_to_css.py`，60 行），不是 §1.8 说的 **Terrazzo**。token 通路的结论不受影响，但正式实现应换 Terrazzo
- 页面顶部的**「演示导轨」不是设计产物**，纯粹为了跳屏和触发失败分支
- `OP1`/`OP2` 是**桩**；真实系统里是后端的事

**规模数字**：

| 部分 | 行数 | 谁写 |
|---|---|---|
| 映射层 | **560**（核心 519） | 我们 |
| 渲染宿主（app/catalog/registry/nav/main/index.css） | **217** | 我们 |
| 组件实现 | **0** | 第三方 |
| 渲染器 / tree-walk / 布局 / 状态 / 校验 | **0** | 第三方 |

## 四、对 §1.8 的处置建议

| §1.8 的表述 | 建议 |
|---|---|
| 性质 1「窄屏堆叠是渲染器的决定」 | **收窄**：渲染器决定"怎么画"，不负责"重新编排"；窄屏降级是**映射层或 catalog** 的责任 |
| 三层架构（语义件 / catalog / 渲染器） | **改成两层**：实际是 `语义件 → 映射层 → 原语组件树 → 渲染器`；"catalog 薄封装"在现成原语目录下是空的 |
| 状态「待 demo 验证」 | → **已验证，形态成立**；附本报告的三处修正 |
| 成本表 ~400–800 行 | → **实测 560 行**，估算准确 |
| 「导出目标 = HTML」 | → **成立**：单文件自包含 HTML，双击即开、可点 |
| 新增记录 | ①`children` 必填（以校验器为准）②失败分支的隐式约定需补纪律 ③跨屏数据流需建模 |
